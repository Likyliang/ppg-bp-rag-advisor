# 高血压 PPG 估算解释 RAG-Agent 本周汇报（展示版）

日期：2026-05-21  
项目：PPG 血压估算结果解释与安全约束 RAG-Agent Demo

## 1. 本周工作定位

本周重点放在 RAG 知识库和评估链路建设上，目标是让系统的证据来源更清楚、检索结果更可审计、安全边界更稳定。

系统的输入不是开放式问诊，而是小程序已经输出的结构化 PPG 估算结果，包括估算收缩压、舒张压、心率、PPG 置信度、信号质量、采集时长、算法版本、测量来源和症状标记等。当前系统只负责对这些估算结果做健康解释、证据检索和安全提醒，不验证 PPG 血压算法准确性，也不用于诊断、治疗、开药、停药或替代规范血压计测量。

本周主要完成三类工作：

1. 扩充和整理文献库，重点补充 PPG 信号质量、无袖带设备边界和家庭血压监测资料。
2. 完善 source catalog，让每个来源都有证据等级、适用场景和安全使用边界。
3. 建立自动化评估链路，验证检索质量、安全过滤、结构化病例和 API 接口稳定性。

## 3. 文献进入 RAG 的流程

文献不是直接丢进向量库，而是经过固定治理流程后再入库。

第一步是归档和登记：记录题名、DOI/PMID、官方链接、下载状态、保存路径和访问说明。PDF 全文只保存在本地 ignored 目录，不提交 Git。

第二步是进入 source catalog：为每个来源标注 evidence_class、allowed_uses、source_quality_score、review_status 和 source_hash。这样可以明确一篇文献能用于哪些场景，不能用于哪些场景。

第三步是写中文摘要 notes：只提取和系统任务相关的内容，包括关键结论、适用范围、引用信息和安全边界。比如 PPG 论文可以用于解释运动、光照、接触压力、肤色和采集时长为什么影响信号质量，但不能用于支持诊断或治疗建议。

第四步是切分为 RAG chunks：把整理后的 notes 切成可检索的小段证据，并保留来源 ID、主题、证据等级和允许用途。当前知识库已经形成 524 个 chunks。

## 4. Source Catalog 的作用

source catalog 相当于知识库的准入表和使用说明书。它解决的核心问题是：RAG 不应该只看文本相似度，还要知道证据是否足够权威、是否适合当前场景。

当前 catalog 的使用规则包括：

1. 急症、用药、孕妇、CKD、糖尿病等高风险场景，优先使用指南、科学声明、官方健康教育或项目安全规则。
2. PPG 和无袖带设备论文只用于解释技术局限、信号质量和研究背景，不支持临床诊断或用药决策。
3. 生活方式资料只用于健康教育，如减盐、运动、睡眠、体重管理等，不承诺治疗效果。
4. 检索结果会结合 allowed_uses 和 evidence_class 过滤，避免把研究背景材料误用成医疗建议依据。

当前审计结果显示：无缺失主题、无重复 source hash、无 orphan source，unsafe source leakage 为 0。

## 6. 自动化测试与实验设计

本周建立了一套更完整的自动化测试和评估体系，重点不是只看系统能不能运行，而是检查它是否检索到合适证据、是否遵守安全边界、是否能处理小程序的结构化输入。

测试覆盖内容包括：

1. 小程序输入字段和别名归一化。
2. 低质量 PPG、采集时间短、置信度低时的保守提醒。
3. 180/120 以及胸痛、气短、肢体无力等症状的安全规则。
4. 检索证据是否命中正确主题。
5. 用药、孕妇、CKD、糖尿病等场景是否使用高可信来源。
6. Safety Agent 对诊断、开药、停药、替代血压计等越界表达的拦截。

检索问题集目前有 100 条，覆盖 PPG 局限、信号质量、家庭复测、急症、用药、特殊人群、生活方式和设备验证。评估时只给检索器问题本身，不把标准答案或 expected_uses 提前喂给它，因此更接近真实使用场景。

结构化病例 fixtures 目前有 50 个，模拟小程序可能输出的不同情况，例如正常值、偏高、低质量信号、180/120 无症状、180/120 伴胸痛、孕妇、糖尿病、CKD 和正在服药用户。

API 链路实验也使用 50 个病例进行验证，重点检查规则预览、知识库检索、结构化响应和安全字段是否稳定。实验允许并行，但最大并发限制为 5，避免后续接入 LLM 或更大规模实验时造成请求过载。
