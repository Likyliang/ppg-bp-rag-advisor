## 2. 系统输入边界：小程序结构化输出

需要特别说明的是，这个系统不是一个开放式问诊系统，输入不是用户随意描述的病情文本，而是小程序上游算法已经输出的结构化 PPG 估算结果。RAG-Agent 的任务是对这些结构化结果做保守解释、复测建议、证据引用和安全审查。

当前核心输入包括：

| 输入类别 | 字段示例 | 用途 |
| --- | --- | --- |
| 估算血压值 | `estimated_sbp`、`estimated_dbp` | 判断本次估算值处于哪个参考范围，只使用 `estimated_bp_category`，不输出诊断 |
| 心率 | `heart_rate` | 作为本次测量上下文展示，不单独做疾病判断 |
| PPG 置信度 | `confidence` | 低置信度时降低解释强度，触发重新采集或规范血压计复核建议 |
| PPG 信号质量 | `signal_quality_score`、`signal_quality_label` | 判断本次估算是否可解释，低质量时优先提示重测 |
| 采集信息 | `capture_duration_sec`、`ppg_source`、`algorithm_version`、`calculation_principle` | 记录采集时长、来源和算法版本，支持审计与报告解释 |
| 用户基础信息 | 年龄、孕妇、糖尿病、CKD、既往心血管病、是否正在服用降压药 | 只用于更保守的复核和就医提醒，不用于诊断或调药 |
| 症状信息 | 胸痛、气短、视物改变、说话困难、肢体无力、严重头痛等 | 与严重偏高估算值组合时触发急症安全规则 |

因此，当前测试和报告 fixtures 也围绕“小程序结构化输出”设计：例如 `145/92 + 心率 + 信号质量 0.86 + 置信度 0.68`、`150/95 + 低信号质量`、`185/122 + 胸痛`、`孕妇/糖尿病/CKD 用户 + PPG 估算偏高` 等。这样更贴近真实应用链路：上游负责估算，本系统负责解释、证据检索和安全约束。

## 4. 文献拿到后做了什么

每拿到一篇文献后，不是直接扔进向量库，而是按固定流程进行治理。

1. 记录来源信息  
   把网页端返回的标题、下载链接、DOI、PMID、官方落地页、访问状态、可信度和保存路径整理成 JSON/Markdown 记录，方便后续审计。

2. 归档 PDF  
   将 PDF 复制到 `knowledge_base/sources/downloads/`。该目录被 Git 忽略，只做本地归档，不提交全文。

3. 建立 source catalog  
   每个来源都登记 source_id、标题、组织/期刊、URL、DOI/PMID、年份、语言、地区、主题、证据等级、筛选分、allowed_uses、版权说明和安全边界。

4. 写中文摘要 notes  
   对 PDF 内容做中文摘要，只记录“可用于报告的要点”和“不能越界使用的边界”。例如 PPG 研究论文只用于解释信号质量和设备局限，不能支持诊断或治疗建议。

5. 生成 RAG source notes  
   系统会把 source catalog 和摘要 notes 转成 Markdown source notes，按主题组织，例如 `measurement_quality`、`home_bp_monitoring`、`cuffless_ppg_limitations`、`emergency` 等。

6. 生成 chunks  
   Ingest 脚本会把 source notes 切分成带 metadata 的 RAG chunks。当前共生成 524 个 chunks。每个 chunk 都带有来源、主题、证据等级和 allowed_uses，所以后续检索时可以做安全过滤。

7. 审计和评估  
   每次知识库更新后，都运行 audit、retrieval evaluation、report evaluation 和 pytest，确认没有重复来源、没有 orphan source、没有不安全来源泄漏。

8. 同步 Obsidian  
   将 PDF 以 symlink 方式维护到 Obsidian 文献库，同时生成 MOC、topic hub、单篇文献 notes 和未下载名单。这样人工阅读和系统 RAG 使用是打通的。

## 5. Source catalog 来源治理系统

本周另一个重点是把文献来源统一纳入 source catalog 管理。source catalog 可以理解为这个 RAG 系统的“文献准入表”和“证据身份证”。每一个来源在进入知识库之前，都必须先经过 source catalog 记录和筛选，而不是下载到 PDF 后直接进入检索库。

每条 source catalog 记录主要包含：

| 字段 | 作用 |
| --- | --- |
| source_id | 给每个来源一个稳定 ID，后续 chunks、引用、报告 evidence 都通过它追溯 |
| title / organization | 记录文献标题、机构或期刊来源 |
| URL / DOI / PMID | 保证来源可以被复查和定位 |
| year / language / region | 记录年份、语言和地区，方便区分 AHA、中国指南、ESC、WHO 等来源 |
| topic | 标注主题，例如家庭血压监测、PPG 信号质量、急症、用药安全等 |
| evidence_class | 标注证据类型，例如 guideline、scientific_statement、validation_standard、review、research_context |
| allowed_uses | 限制这个来源能用于什么场景，例如 signal_quality、home_bp_monitoring、emergency_alert |
| screening score | 根据权威性、时效性、相关性、可访问性、安全适用性打分 |
| review_status | 标记是否纳入知识库 |
| source_hash | 用于检测重复来源 |

这样做的意义是：RAG 不只是“检索相关文字”，而是先知道每个来源“是什么等级、能用于什么、不能用于什么”。例如 PPG 运动伪差论文可以用于解释信号质量，但不能用于急症判断；生活方式网页可以用于健康教育，但不能支持用药调整；急症、孕妇、CKD、糖尿病等敏感场景必须优先使用指南、科学声明、官方健康教育、验证标准或安全规则。

当前 source catalog 处理结果：

| 项目 | 结果 |
| --- | ---: |
| 正式纳入来源 | 114 |
| source catalog 校验问题 | 0 |
| duplicate source hash | 0 |
| orphan source | 0 |
| 主题缺口 | 0 |
| unsafe source leakage | 0 |

也就是说，现在系统里的每个 RAG chunk 都能追溯到 source catalog 中的来源记录，并且可以根据 evidence_class 和 allowed_uses 做检索过滤。这是后续报告可审计、安全边界可控的基础。

本周很重要的一部分工作是把验证流程自动化。现在系统不是靠人工感觉“应该没问题”，而是每次更新知识库后都运行质量门禁。

当前自动化测试包括 223 个测试点，主要覆盖：

| 测试类别 | 测试内容 |

## 10. 当前 RAG 的组织原理

本系统采用 metadata-governed RAG，而不是简单地把论文全文丢进向量库。

核心原则是：

1. 每个来源先经过 source catalog 筛选。
2. 每个 chunk 都带 evidence_class、topic、allowed_uses、source_quality_score。
3. 检索时先判断问题意图，再按用途过滤证据。
4. 高风险场景只能使用高可信来源。
5. 报告中的每条建议必须绑定 evidence。
6. Safety Agent 最后检查是否出现诊断、治疗、开药、停药、设备替代血压计、急症安抚等违规内容。

例如，如果用户问“185/122 还有胸痛怎么办”，系统不能只检索 PPG 论文，也不能给出普通生活方式建议，而必须优先返回急症规则、AHA/CDC/指南类高可信来源，并输出及时就医/急救相关提醒。相反，如果用户问“运动会不会影响 PPG”，系统可以使用 PPG 信号质量综述或研究论文，但这些来源只能解释信号质量，不能扩展成临床诊断建议。

## 12. 汇报用总结

本周我主要完成了高血压 PPG 估算解释 RAG-Agent 的知识库扩充和评估闭环建设。系统输入边界已经明确为小程序上游输出的结构化 PPG 估算结果，包括估算血压值、心率、PPG 置信度、信号质量和采集信息；RAG-Agent 只负责解释、复测建议、证据检索和安全约束。当前本周已归档并维护 62 份完整 PDF 文献/资料；所有来源先经过 source catalog 治理，记录证据等级、主题、筛选分和 allowed_uses，筛选后纳入 114 个正式来源，并生成 524 个带 metadata 的 RAG chunks。为了保证系统不是“能生成就行”，我同时建立了自动化测试和评估体系，包括 223 个测试点、100 条 golden queries 检索问题集和 50 个标准病例报告 fixtures。当前严格质量门禁全部通过，检索 Precision@5 为 1.0，敏感场景高可信证据引用率为 1.0，unsafe source leakage 为 0；实验评估支持并行但最大并发限制为 5。下一步会继续处理剩余 PDF 摘要、维护未下载清单、扩展真实用户问题集，并强化 Demo 和论文实验展示。
