日期：2026-05-21  
项目：PPG 血压估算结果解释与安全约束 RAG-Agent Demo

## 1. 本周工作概述

本周主要围绕高血压 PPG 估算解释系统继续完善 RAG 知识库和评估闭环。当前系统不是一个开放式问诊工具，而是接收小程序上游输出的结构化 PPG 估算结果，例如估算收缩压/舒张压、心率、PPG 置信度、信号质量、采集时长、算法版本和症状信息。系统的任务是对这些结果做保守解释、复测建议、证据引用和安全审查，不验证 PPG 血压算法本身，也不做诊断、治疗、开药、停药或替代规范血压测量。

本周的核心成果可以概括为：文献更多了，来源更可审计了，RAG 检索更有安全边界了，接口链路和评估体系也更稳定了。

## 3. 文献拿到后做了什么

为了避免把 PDF 直接丢进知识库造成来源混乱，我把文献处理固定成了一套流程：

1. 记录下载结果  
   保存题名、DOI/PMID、官方链接、下载状态、访问说明和保存路径。

2. 归档 PDF  
   PDF 全文只保存在本地 ignored 目录，不提交到 Git 仓库。

3. 建立 source catalog  
   每个来源都登记来源 ID、机构/期刊、年份、主题、证据等级、筛选分和 allowed_uses。

4. 写中文摘要 notes  
   只整理可用于解释、提醒和引用的要点、citation 和安全边界。例如 PPG 研究论文只能用于解释信号质量和设备局限，不能用于诊断或治疗建议。

5. 生成 RAG chunks  
   系统把整理好的 source notes 切成 524 个带 metadata 的证据片段，后续检索、解释和引用都可以追溯来源。

6. 审计和评估  
   每次更新知识库后，运行 source audit、retrieval evaluation、API experiment 和 pytest，检查是否有重复来源、主题缺口、安全来源泄漏或医学边界问题。

7. 同步 Obsidian  
   将文献同步到 Obsidian，建立 MOC、topic hub、单篇文献 notes 和未下载名单，方便后续人工阅读和继续扩充。

## 4. Source catalog 的作用

Source catalog 可以理解为这个 RAG 系统的“文献准入表”。它解决的问题是：不是所有文献都能用于所有建议。

例如：

- 高血压指南、科学声明和官方健康教育可以支持复测、就医提醒、急症规则和安全边界。
- PPG/无袖带设备论文可以解释运动、光照、接触压力、肤色、采集时长等信号质量问题。
- 单篇 PPG 或机器学习论文不能用来支持“可以不用就医”“可以停药”“可以替代血压计”这类结论。

所以每个来源都会标注：

| 字段 | 作用 |
| --- | --- |
| evidence_class | 标明它是指南、科学声明、官方健康教育、综述还是研究背景 |
| allowed_uses | 限制它能用于哪些场景，例如信号质量、家庭复测、急症提醒、用药安全 |
| source_quality_score | 记录权威性、时效性、相关性和可访问性评分 |
| source_hash | 用来发现重复来源 |

当前 source catalog 审计结果是：无缺失主题、无重复 source hash、无 orphan source，unsafe source leakage 为 0。

## 5. RAG 知识库目前覆盖什么

当前知识库覆盖 10 类主题：

| 主题 | 作用 |
| --- | --- |
| PPG/测量质量 | 解释运动、光照、肤色、接触压力、测量位置、采集时长等影响 |
| 家庭血压监测 | 支持复测、记录和规范测量建议 |
| 血压分类 | 支持 estimated_bp_category 的参考范围解释 |
| 急症提醒 | 支持 180/120 及胸痛、气短、神经症状等安全规则 |
| 用药安全 | 防止根据 PPG 估算结果自行停药、调药 |
| 特殊人群 | 孕妇、糖尿病、CKD、老年人、心血管病史等保守提醒 |
| 无袖带/PPG 局限 | 说明 PPG 估算不能替代规范血压测量 |
| 验证设备 | 支持上臂式血压计、验证设备和设备注册表相关建议 |
| 生活方式 | 支持减盐、运动、睡眠、体重、戒烟限酒等健康教育 |
| 免责声明 | 明确系统不能诊断、治疗或替代医生 |

本周增强最明显的是 PPG 信号质量和无袖带设备边界。现在系统能更有依据地解释为什么运动、接触压力、环境光、肤色、传感器位置和采集时长会影响 PPG 估算结果。

## 6. 自动化测试和实验

本周把系统验证做成了比较完整的自动化流程。

自动化测试覆盖：

- 小程序结构化输入字段和字段别名。
- 规则引擎的血压范围、低质量信号、采集时长、急症规则。
- RAG 检索是否命中正确主题。
- Safety Agent 是否拦截诊断、开药、停药、设备替代血压计等越界表达。
- 解释建议是否绑定 evidence。
- API 是否能正常完成规则预览、知识库搜索和结构化响应。

此外，我设计了两类实验集：

1. Golden queries  
   共 100 条问题，覆盖 PPG 局限、信号质量、家庭复测、急症、用药、孕妇、糖尿病、CKD、生活方式和设备验证。评估时只把问题交给检索器，不把标准答案传进去，所以结果更接近真实检索。

2. 结构化病例 fixtures  
   共 50 个病例输入，模拟小程序实际输出，例如正常值、偏高值、低质量信号、180/120 无症状、180/120 伴胸痛、正在用药、孕妇、糖尿病、CKD 等。

为了验证真实 API 链路，我还做了一轮轻量 API 实验，重点检查规则预览、知识库检索、结构化响应和安全字段是否稳定。实验并发限制为 5，避免后续接入 LLM 或更大实验时请求过载。完整报告生成和前端展示放到下周继续完善。
