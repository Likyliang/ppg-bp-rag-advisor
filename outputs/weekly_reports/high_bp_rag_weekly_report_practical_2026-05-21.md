## 1. 这周主要做了什么

这周我主要在补 RAG 知识库和整理评估流程。之前系统已经能跑起来，但知识来源还比较分散，所以这周重点不是做新界面，而是把文献、来源记录、检索评估和安全边界先打牢。

这个系统的输入也重新梳理了一下：它不是开放式问诊，而是接收小程序已经算出来的 PPG 血压估算结果，比如估算收缩压、舒张压、心率、PPG 置信度、信号质量、采集时长和症状信息。系统后面做的是解释和安全提醒，不验证 PPG 血压算法准确性，也不做诊断、治疗、开药、停药，不能替代规范血压计测量。

简单说，这周主要完成了三件事：

1. 把文献库继续扩充和归档，尤其补 PPG 信号质量和无袖带血压设备边界。
2. 把来源整理进 source catalog，让每条证据都知道“能用在哪里、不能用在哪里”。
3. 做了一轮检索和 API 链路实验，确认知识库、检索、安全过滤和接口基本稳定。

## 3. 拿到文献以后怎么处理

这部分我现在已经整理成固定流程了，不是把 PDF 直接丢进向量库。

首先，我会记录每篇文献的题名、DOI/PMID、官方链接、下载状态和保存路径。PDF 全文只放在本地 ignored 目录，不提交到 Git。

然后，每个来源都会进入 source catalog。这里会记录它是什么来源，比如指南、科学声明、官方健康教育、综述还是研究论文；也会标出它适合用于什么场景，比如家庭复测、信号质量解释、急症提醒、用药安全等。

接着，我会写中文摘要 notes。摘要里只保留对系统有用的内容，比如可以用于解释的要点、citation 和安全边界。举个例子，PPG 相关论文可以用来解释运动、光照、接触压力、肤色和采集时长为什么会影响结果，但不能用来支持“可以不用就医”或“可以停药”。

最后再把这些整理好的 source notes 切成 RAG chunks。目前已经生成了 524 个 chunks。可以把 chunk 理解成系统检索时真正使用的小证据片段，每个片段都能追溯到原始来源。

## 4. 为什么要做 source catalog

我觉得这周比较重要的一点是把 source catalog 做扎实了。它相当于知识库的“准入表”，能避免 RAG 只按文字相似度乱引用材料。

比如：

- 急症、用药、孕妇、CKD、糖尿病这些高风险场景，必须优先用指南、科学声明、官方健康教育或安全规则。
- PPG 信号质量论文只能用来解释技术局限，不能用来判断用户是不是有病。
- 生活方式材料可以支持减盐、运动、睡眠这类健康教育，但不能支持调药。

现在每个来源都会带上 evidence_class、allowed_uses、source_quality_score 和 source_hash。这样检索时不只是看“像不像”，还会看这个来源“够不够权威、能不能用于这个场景”。

当前 source catalog 审计结果比较干净：没有缺失主题，没有重复 source hash，没有 orphan source，unsafe source leakage 是 0。

这周增强最明显的是 PPG 信号质量和无袖带设备边界。现在如果后面要解释“为什么这次 PPG 估算不一定可靠”，知识库里已经有比较具体的依据，比如运动伪差、接触压力、环境光、肤色差异、传感器位置和采集时长。

## 6. 测试和实验做了什么

我这周也把测试做得更系统了一些。现在不是只看系统能不能跑，而是用一套固定测试检查它有没有越界、检索准不准、API 链路稳不稳定。

测试主要覆盖：

- 小程序结构化输入字段和别名能不能正常解析。
- 低质量 PPG、采集时间短、置信度低时是否会触发保守提醒。
- 180/120 以及胸痛、气短、肢体无力等症状能不能触发安全规则。
- 检索出来的证据是不是落在正确主题。
- 用药、孕妇、CKD、糖尿病等场景有没有使用高可信来源。
- Safety Agent 是否能拦截诊断、开药、停药、替代血压计等越界表达。

另外我准备了两组实验数据：

1. 100 条 golden queries  
   这些是检索问题集，覆盖 PPG 局限、信号质量、家庭复测、急症、用药、特殊人群、生活方式和设备验证。评估时只把问题给检索器，不把答案喂进去，所以更接近真实情况。

2. 50 个结构化病例 fixtures  
   这些是模拟小程序输出的病例输入，比如正常值、偏高、低质量信号、180/120 无症状、180/120 伴胸痛、孕妇、糖尿病、CKD、正在服药等。

我还额外跑了一轮轻量 API 链路实验，重点不是正式展示报告，而是检查现有接口在规则预览、知识库检索、结构化响应和安全字段上是否稳定。实验并发限制为 5，后面接 LLM 或更大实验时也不会一下子把请求打得太猛。
